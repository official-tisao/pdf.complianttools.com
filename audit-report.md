# FillFormWorkspace and +page.svelte SSR / Form-Fill Audit

**Date**: 2026-11-10  
**Scope**: `FillFormWorkspace.svelte` and `fill-form/+page.svelte`  
**Goal**: Identify all remaining issues that could cause `ReferenceError: document is not defined` or other SSR problems, plus form-filling correctness and design issues.

---

## Executive Summary

Two confirmed **high-severity** regressions from the new root layout import:

| #   | Issue                                                                                                                                                                                                                                 | Severity                 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| B1  | Root layout (`+layout.svelte`) now **eagerly imports** pdfium bootstrap, pulling the 4.4 MB `@embedpdf/pdfium` graph into **every** route — including the landing page — directly contradicting the comment in `configure-pdfium.ts`. | **High** (bundle budget) |
| B4  | The pdf.js worker URL path (`legacy/build/pdf.mjs`) **may not exist** in the pinned v6.3.289; `loadPdfJs()` will reject at runtime on the first PDF open.                                                                             | **High** (verify)        |

All other findings below are either **already known**, **low risk**, or **pre-existing** — they do not cause an immediate `ReferenceError: document is not defined` on SSR, but some do affect correctness, performance, or UX.

## Category D — Runtime / SSR‑Execution Hazards

| ID  | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Lines                              | Severity                                                                                                                                                                                                         |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Three `$effect` blocks and `onDestroy` reference `document`, `loadingTask`, etc. Under **SSR**, Svelte skips `$effect` execution, but the module script is still evaluated. The `document.addEventListener` in the effect and `document.activeElement` in `handleKeydown` are guarded by `browser`, which is correct. | D3  | `loadAnnotations` uses `bytes!` non-null assertion after guarding `if (!pdfDoc                                                                                                                                                                                                                                                                                                                                                                                                                                                |                                    | !bytes) return`. | D4  | `renderPage` has **no error boundary** around the render path. ## Category E — Keyboard Navigation / Focus Management

| ID  | Finding                                                                                                                                                                                                                                                                                                                                                                                                                           | Lines                           | Severity    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ----------- |
| E1  | `focusNextField` has **three near‑duplicate page‑walk loops** (forward‑same-page, forward‑wrap, backward‑wrap). All three use the **same** selector `'[data-field-name] input, [data-field-name] textarea, [data-field-name] select'`, which matches the **first** input in DOM order — **not** the field at the computed `nextIndex`. Tab across a page boundary always jumps to the page's first field, ignoring logical order. | `focusNextField`, lines 521‑609 | Medium (UX) |
| E2  | `handleKeydown` is attached to **`document`**, not the component root. A global `keydown` fires for the entire document, including the address bar. It calls `event.preventDefault()` on Tab, arrows, `+`, `-`, `0`, `Home`, `End` whenever `!isInInput` — which is most of the time. Can interfere with browser chrome and other simultaneous interactions.                                                                      | `handleKeydown`, line 641       | Low         |
| E3  | `isInInput` only checks **tag names**, not `role`. A `<div contenteditable>` or element with `role="combobox"` would be treated as "not in input," so arrow/zoom keys fire while the user is editing such an element.                                                                                                                                                                                                             | `handleKeydown`, lines 486‑488  | Low         |
| E4  | The keyboard listener is added in a `$effect` but **also removed in `onDestroy`**. Both call `document.removeEventListener('keydown', handleKeydown)`. On rapid navigation, both removal paths may fire — not a bug today, but a maintenance hazard.                                                                                                                                                                              | lines 633‑644                   | Low         |

## Category F — Form‑Field Rendering Correctness

| ID  | Finding                                                                                                                                                                                                                                                                                                                                                                                                       | Lines                               | Severity               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ---------------------- |
| F1  | **Text and textarea branches never set `input.disabled`** for readonly fields. The wrapper sets `pointer-events: none` and `opacity: 0.5` (making it look faded), but the `<input>` is fully interactive. Combined with C1 (readonly flag never populated), every field renders as editable.                                                                                                                  | `createFieldOverlay`, lines 251‑302 | **High** (correctness) |
| F2  | Radio buttons are **not properly grouped**: each widget annotation produces its own `<input type="radio">` with `name="radio-${fieldName}"`. Only one `<input>` is created per annotation (code comment admits _"in reality we'd need all options"_). The value written back is the radio's own `value` attribute, not the option label, so `fillFormPdf`'s `select(String(value))` receives an opaque token. | `createFieldOverlay`, lines 325‑350 | Medium                 |
| F3  | **Dropdown options are never populated**: only a placeholder and, if a current value exists, one `<option>` mirroring that value. The actual PDF choice list is never read. Comment at line 363 acknowledges this. A user opening a dropdown sees at most one option plus a placeholder.                                                                                                                      | `createFieldOverlay`, lines 352‑394 | Medium                 |
| F4  | `fieldValues` is **spread on every input event** (`fieldValues = { ...fieldValues, [fieldName]: value }`), creating a new object per keystroke. For a large form this is O(n) per keystroke and also causes every consumer of `fieldValues` to re‑run. `updateStatus()` is called on every input event too, re‑deriving status text synchronously.                                                            | Throughout `createFieldOverlay`     | Low                    |
| F5  | `dirty` is set on first edit but **never cleared** except on download. If the user edits a field and reverts it to its original value, `dirty` stays `true` and the status bar continues to claim "unsaved changes." No diff against original values.                                                                                                                                                         | lines 269, 317, 343, 388, 624       | Low                    |

## Confirmed New Regressions (Requiring Fix)

| Priority | Issue                                                     | What to Fix                                                                                                                                                                      |
| -------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1**    | **B1** — Root layout eagerly imports pdfium bootstrap     | Remove `import '$lib/configure-pdfium'` from `+layout.svelte`, or make it lazy using the `?url` pattern (like `configure-pdfjs.ts`).                                             |

| **3**    | **C1** — `readonly` never populated by engine             | Either (a) add `readonly` to `FormFieldInfo` from the pdf.js widget annotation, or (b) stop reading it in `createFieldOverlay` and rely on the wrapper's `pointer-events: none`. |
